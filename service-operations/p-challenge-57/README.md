## 課題 1

### 問題 1

ログレベルとは、システムやアプリケーションが動作中に出力するログメッセージを、重要度や緊急度に応じて分類するための指標です。
この仕組みにより、開発者や運用者はログの内容を整理して分析し、問題の原因を特定したり、解決に役立てたりすることができます。

### 問題 1-1

ログレベルには、システムやアプリケーションの動作中に発生するメッセージを重要度や緊急度に応じて分類する役割があります。
これにより、開発者や運用者はどのメッセージを優先的に確認すべきかを判断しやすくなります。

使用するプログラミング言語やフレームワークによって、ログレベルの名称や定義が異なる場合がありますが、基本的な考え方は共通です。
たとえば、Javaで広く利用されるログフレームワーク「log4j」では、以下のようなログレベルが定義されています。

| Name | Priority |
| ---- | ---- |
| OFF | 0 |
| FATAL | 100 |
| ERROR | 200 |
| WARN | 300 |
| INFO | 400 |
| DEBUG | 500 |
| TRACE | 600 |
| ALL | Integer.MAX_VALUE |

[Levels](https://logging.apache.org/log4j/2.x/manual/customloglevels.html)

ログレベル色々
[ログレベル色々](https://zenn.dev/log4cat/articles/log-levels-journey)

多くの場合、ログレベルは以下の2つのカテゴリに分類されます。

1. 重大なログレベル
    - 主に FATAL、ERROR、WARN などが該当します。
    - これらのログレベルは、システム管理者に修正が必要な問題を通知するために使われます。
2. それほど重大でないログレベル
    - 主に INFO、DEBUG、TRACE などが該当します。
    - これらのログレベルは、システム管理者や開発者が問題の原因を診断するための情報を提供します。

### 問題 2

- アプリケーションログにはどのような情報を含めるべきでしょうか？

| 項目 | 概要 | 例・補足 |
| ---- | ---- | ---- |
| 日時 | ログを出力した時間。 年月日時分秒ミリ秒。JST、UTC などタイムゾーン要確認。 必ず出力する。 | 例）2025-01-16 10:23:45.123最低でもミリ秒単位で出力すると、処理の前後関係を正しくトレースしやすい。 |
| イベント ID | 一連のイベントをトレースするための識別子。必要に応じて設定する。 | 例）Event-0001 同じイベント内で複数の操作が行われた場合、共通のイベント ID を利用すると紐づけやすい。 |
| リクエスト ID | リクエスト単位で付与する識別子。 (イベント ID との使い分け・併用は運用設計次第) | 例）Req-abcdef123456 外部 API と連携する場合やマイクロサービス間のリクエストを追跡する際に特に有効。 |
| ログレベル | ログの重要度・緊急度を表す。 例：DEBUG / INFO / WARN / ERROR / FATAL | 運用監視ツールやクラウドサービスによっては、ログレベルでフィルタリング・アラート設定を行う。 |
| イベント種類 | どのイベント（処理）に関するログか。 関数名や API パス名、バッチ名など。 | 例）DELETE /users/{id} / sendEmail() / batch_cleanup_job |
| リクエスト対象 | どの URL や API、サーバーに対してリクエストを行ったか。 | 例）https://api.example.com/v1/user/123 |
| ユーザー情報 | リクエストを実行したユーザーやクライアントの識別情報。 ユーザー ID、IP アドレスなど。 | 例）user_id=U12345, ip=10.0.0.1 匿名ユーザーやバッチ処理などの場合は、適切な識別子を付与する。 |
| 関連リソースの情報 | 処理対象となったリソースやテーブルの ID、キーなど。 | 例）ユーザー更新の場合：table=user, user_id=123 複数テーブル更新時、各テーブルのレコード ID をまとめてログに出力する。 |
| 処理内容 | どのような操作（処理）を行ったか。 例：GET / POST / PUT / DELETE | 例）DELETE / batch cleanup |
| 処理結果 | 処理の成否、実行件数、処理時間、エラーコードなど。 | 例）success / fail / updated=10 / elapsedTime=120ms 後から性能評価やトラブル原因調査を行うための指標として重要。 |
| メッセージ | 任意の詳細情報や補足説明、エラーメッセージなど。 ログレベルがエラー以上の場合に特に重要。 | 例）errorCode=404, message="User not found" エラーの原因究明に役立つ。 |


ログに含めない方が良い情報
	1.	個人情報 (PII: Personally Identifiable Information):
	•	ユーザーの氏名、住所、電話番号、メールアドレス。
	•	クレジットカード番号や銀行口座情報。
	•	生年月日、社会保障番号（SSN）、マイナンバーなどの機密情報。
	2.	認証情報:
	•	パスワードやパスフレーズ。
	•	APIキー、トークン（例: JWTトークン）、秘密鍵。
	•	OAuthのアクセストークン。
	3.	機密情報:
	•	社内の機密データやビジネス上の秘密。
	•	暗号化されていないデータ（例: 機密文書の内容）。
	4.	過剰なデバッグ情報:
	•	生成された膨大なログデータ（特に運用環境で不要なもの）。
	•	未加工の入力データ（例: ユーザーが入力したすべての内容）。
	5.	他者に悪用される可能性がある情報:
	•	環境変数（例: 環境固有の設定値やパス）。
	•	サーバーやインフラの内部構造に関する詳細。

    推奨事項
	•	匿名化とマスキング:
個人情報や機密情報がどうしてもログに含まれる場合は、ハッシュ化やマスキングを行い直接識別できないようにする。
	•	ログローテーションと削除ポリシー:
ログが肥大化しないよう、定期的なログローテーションや古いログの削除を実施。
	•	暗号化:
機密性の高いログファイルは保存時や転送時に暗号化する。
	•	アクセス制御:
ログファイルへのアクセス権限を制限し、認可されたユーザーのみが閲覧できるようにする。

### 問題 6

- 最近ではサービスが稼働するインスタンスにログファイルを保存するのは避けた方が良いプラクティスとして言及されることもあります。それは何故でしょうか？
    - food for thought 1: 作成されたログファイルの閲覧権限を細かく管理したい時にはどうすれば良いのでしょう？例えばUserに関するログはManager以上の権限を持っていなければ閲覧できないとか。逆に例えばマネージャーが降格してUserに関するログを閲覧不可にする必要が生じた時、誰がどのような手順で管理すれば良いのでしょう？
    - food for thought 2: 特定のログを誰が閲覧したか、または誰が編集したか、どのように確認すれば良いのでしょう？
    - food for thought 3: 仮に複数のインスタンス（10個ぐらい）でサービスが運用されていて、リクエストを処理する途中で複数のインスタンスにログが分散したとします。このようなログをどうやって集約すれば良いのでしょう？
    - food for thought 4: システムのストレージ容量をログファイルが食い尽くしてしまうことはないのでしょうか？
