# 課題 57

## 課題 1

### 問題 1

ログレベルは、システムやアプリケーションが出力するログメッセージを重要度や緊急度に応じて分類する指標です。
これにより、開発者や運用者はログを整理・分析し、問題の特定や解決に役立てることができます。

### 問題 1-1, 1-2

ログレベルは、システムやアプリケーションの動作中に発生するメッセージを重要度や緊急度に応じて分類する役割を持ちます。
これにより、開発者や運用者は、どのメッセージを優先的に確認すべきか判断しやすくなります。

使用するプログラミング言語やフレームワークによってログレベルの名称や定義は異なりますが、基本的な考え方は共通です。
たとえば、Javaで広く使われるログフレームワーク「log4j」では、以下のようなログレベルが定義されています。

| Name | Priority |
| ---- | ---- |
| OFF | 0 |
| FATAL | 100 |
| ERROR | 200 |
| WARN | 300 |
| INFO | 400 |
| DEBUG | 500 |
| TRACE | 600 |
| ALL | Integer.MAX_VALUE |

[Levels](https://logging.apache.org/log4j/2.x/manual/customloglevels.html)

ログレベル色々
[ログレベル色々](https://zenn.dev/log4cat/articles/log-levels-journey)

一般的に、ログレベルは以下の2つのカテゴリに分類されます。

1. 重大なログレベル（FATAL、ERROR、WARN）
    - システム管理者に修正が必要な問題を通知するために使用されます。
2. 診断用のログレベル（INFO、DEBUG、TRACE）
    - システム管理者や開発者が問題の原因を特定するための情報を提供します。

### 問題 4

- ログを全て人力で検査するのは大変なので、スクリプトなどで集計しやすいように、パースしやすいメッセージを作ることも大切だと言われます。どのようなログメッセージならパースしやすくなるでしょうか？
  - ヒント：ログ集計によく使われるDataDogはログをパースするパーサーが標準装備されています。[こちらの使い方を読めば、どのようなログがパースしやすくなるか、ヒントが得られるかもしれません](https://docs.datadoghq.com/ja/logs/guide/log-parsing-best-practice/)

1. 構造化されたフォーマットの使用

``` plaintext
<タイムスタンプ> | <ログレベル> | <モジュール名> | <メッセージ> | <属性>
```

2. Key-Value形式の利用

``` plaintext
user_id:12345, action:login, duration:2.34s
```

3. 必要な部分の抽出を想定したフォーマット
各要素（タイムスタンプ、ログレベルなど）の位置や区切りを揃えることで、取り出したい情報（例：user_id など）を抽出できるようにする。

4. 段階的なパース
一度に複雑な正規表現を組むのではなく、日付部分 → ログレベル → メッセージ内容 → 属性 のように段階的に抽出する設計にする。

5. 適切なマッチャーの使用
正規表現ライブラリやパーサーが提供する「スペース以外」「数字のみ」「英数字のみ」といった基本的なマッチャーを活用することで、複雑さを抑えられる。

6. JSONや他の構造化形式の活用
JSON形式でログを出力すると、各種言語・ツール（Elasticsearch、Splunk、Datadog 等）でパースが容易になり、扱いが標準化しやすい。

### 問題 5

### 問題 5-1

アクセスログは、主にWebサーバなどがクライアント（ユーザーやシステム）からのリクエストを受け取った際の情報を記録したログです。

記録内容の例
 • リクエストを行ったクライアントのIPアドレス
 • アクセスしたURL
 • リクエストの日時
 • HTTPメソッド(GET/POSTなど)やHTTPステータスコード(200, 404など)
 • ユーザーエージェント（ブラウザやクローラなどの種類、バージョン）

用途
 • ユーザーやシステムのアクセス傾向を把握する（どのページがどのくらい閲覧されているか、アクセスピークはいつか）
 • セキュリティ上の分析（不正アクセスやクローリング、DOS攻撃の検知など）
 • トラブルシューティング（どのURLにエラーが多いか、いつからレスポンスが遅くなったかの分析）

### 問題 5-2

概要
 • アプリケーションログは、Webアプリケーションや業務システムなどが稼働中に内部で発生したイベント、動作、状態などを記録するログです。
 • ログライブラリ（例: Log4j, Winstonなど）やフレームワーク機能を用いて開発者が任意のタイミングで記録することが多いです。

記録内容の例
 • ユーザーが実行した操作や処理の流れ（「ユーザーAが注文を確定しました」など）
 • アプリケーションの処理開始・終了、タイミング、パラメータ
 • 重要なビジネスロジックでの状態やエラー情報
 • デバッグ用に取得した変数の値、APIのレスポンスなど

用途
 • アプリケーションがどのような処理を行ったかの履歴を追跡する
 • 障害・不具合発生時に原因を特定するために利用する
 • 開発・運用段階でのデバッグやモニタリング

### 問題 5-3

概要
 • エラーログは、システムやアプリケーションがエラーや障害を検知した際に、その詳細やスタックトレース等を記録するためのログです。
 • アプリケーションログやOSのログと分離して扱われることもあれば、アプリケーションログの一部として出力される場合もあります。

記録内容の例
 • 例外発生時のスタックトレース（JavaのNullPointerExceptionなど）
 • エラーが発生した日時、メッセージ
 • どの機能・モジュールでエラーが起きたか

用途
 • 不具合や障害の原因究明に利用（エラーメッセージやスタックトレースからコードの不具合箇所を推測する）
 • システムが正常に動作しているかを監視する
 • 障害発生時の迅速な復旧や対策

### 問題 5-4

概要
 • ユーザーログ（ここではフロントエンドのクライアントサイドログを指す）は、ユーザーのブラウザ上で発生する操作やエラーを記録するログです。
 • SPA（Single Page Application）やモバイルアプリなどクライアントサイドのJavaScript/TypeScriptで記録されることが多く、サーバー側に送信して分析するケースもあります。

記録内容の例
 • ボタンやリンクなどUIの操作履歴（「◯◯ボタンをクリックした」など）
 • フロントエンドで発生したJavaScriptエラー
 • ユーザーが入力したデータや画面遷移
 • フロントエンドとバックエンド間の通信状況・レスポンス

用途
 • ユーザーがどのように画面操作を行っているかを可視化する（UI/UX改善のヒントにする）
 • クライアント側のJavaScriptエラーを早期に発見する（モニタリングツールを組み合わせる）
 • A/Bテストや画面改善施策の効果測定

### 問題 5-5

概要
 • データベースのクエリログは、データベース（RDBMSやNoSQL）に対して実行されたSQLクエリやコマンドなどを記録するログです。

記録内容の例
 • 実行されたSQL文（SELECT, INSERT, UPDATE, DELETEなど）
 • 実行したユーザーやアプリケーションの情報
 • 実行時間、開始時刻・終了時刻
 • クエリの結果（返却された行数など）

用途
 • SQLの実行状況の確認（どのようなクエリが多く発行されているか）
 • パフォーマンスチューニング（遅いクエリの洗い出し、インデックス最適化など）
 • セキュリティ監査（不正なクエリやアクセス権限の確認）
 • データベース障害発生時の原因調査

### 問題 6

### 問題 6-1

サーバやアプリケーションなどが出力するログファイルが大きくなりすぎないように、定期的あるいは一定サイズに達したタイミングでファイルを切り替える（古いファイルを別名にして新しいファイルを生成する、もしくは古いファイルを圧縮/削除するなど）の仕組みを指します。Unix/Linux 系の環境では、主に logrotate コマンドなどを用いて定期的に実施されることが多いです。

### 問題 6-2

ログローテーションのメリット

 1. ディスク使用量の管理が容易になる
ログファイルは放っておくと際限なく巨大化します。定期的にローテーションすることで、ディスクの容量を圧迫しないよう古いファイルを圧縮・削除しやすくなります。
 2. ログ解析の効率化
一つのファイルが大きくなると、解析ツールで処理する際のパフォーマンスが低下することがあります。サイズを分割しておくことで、解析する対象を絞りやすくなり、必要な期間のログだけに対して検索や解析を行いやすくなります。
 3. ログファイル管理の標準的手法
古くからのシステム運用において、運用担当者がログローテーション設定に慣れており、多くの環境で標準的に導入しやすいという利点があります。

ログローテーションのデメリット

 1. 過去ログの検索・分析が煩雑
ローテーションによってログファイルが分割・圧縮されるため、特定の期間にまたがる分析をする際にはファイルを解凍して確認する手間が増えます。またログが細かく分かれていると管理・検索がやや複雑になります。
 2. タイミングによるログの取りこぼしリスク
システム障害が起こった際に、ローテーションと重なると、必要なログがローテーションされた直後のファイルに含まれておらず見落とす可能性が生じることもあります。
（一般的には、タイミングや適切な設定によって取りこぼしを最小限にすることができますが、設計不備があると問題になる場合があります。）
 3. 設定ミスや管理負荷
運用ポリシーに合わせたローテーションの頻度、圧縮や削除のルールを適切に設定する必要があり、環境によっては複雑になります。設定を誤るとログがすぐ削除されてしまう、あるいは思ったよりディスク容量が節約されない、といった運用トラブルに繋がります。

### 問題 6-3

 1. クラウド環境やコンテナ化の普及
 • 近年はコンテナ（Docker など）を用いたマイクロサービス化が進んでいます。コンテナの標準出力に直接ログを出し、それをホスト側やサードパーティのロギングサービスが収集するケースが増えています。
 • また、クラウドのマネージドなロギングサービス（AWS CloudWatch Logs、Azure Monitor、GCP Cloud Logging など）を利用する場合、ログデータはクラウドに集約されるため、サーバローカルでのログファイル管理（ローテーションを含む）をあまり意識しなくてもよくなります。
 2. 分散ログ管理・中央集約型システムの普及
 • Elastic Stack (ELK Stack: Elasticsearch / Logstash / Kibana)、Fluentd、Splunk など、ログをリアルタイムあるいは準リアルタイムで集中管理するプラットフォームが普及してきました。
 • 各サーバでログをローテーションしてローカルに置くよりも、ログを転送・集約し、必要があればそこから参照・解析するほうが運用効率や可観測性（オブザーバビリティ）の面で利点が大きいです。
 3. ジャーナル（journal）管理の浸透
 • Systemd 環境では journald が標準的に稼働し、ログをバイナリ形式でまとめて管理します。ローテーション処理については journald 自身の設定で制御されることが多く、従来型のテキストログを対象にした logrotate をあまり直接利用しないケースも増えています。
 4. 高性能・大容量ストレージの普及
 • ストレージコストが下がり、物理ディスク容量の制限でログを細かくローテーションする必然性が相対的に低下しているのも一因です。（ただし、セキュリティやパフォーマンスの観点からローテーションを行うことは今でも重要です。）

### 問題 7

- 最近ではサービスが稼働するインスタンスにログファイルを保存するのは避けた方が良いプラクティスとして言及されることもあります。それは何故でしょうか？
  - food for thought 1: 作成されたログファイルの閲覧権限を細かく管理したい時にはどうすれば良いのでしょう？例えばUserに関するログはManager以上の権限を持っていなければ閲覧できないとか。逆に例えばマネージャーが降格してUserに関するログを閲覧不可にする必要が生じた時、誰がどのような手順で管理すれば良いのでしょう？
  - food for thought 2: 特定のログを誰が閲覧したか、または誰が編集したか、どのように確認すれば良いのでしょう？
  - food for thought 3: 仮に複数のインスタンス（10個ぐらい）でサービスが運用されていて、リクエストを処理する途中で複数のインスタンスにログが分散したとします。このようなログをどうやって集約すれば良いのでしょう？
  - food for thought 4: システムのストレージ容量をログファイルが食い尽くしてしまうことはないのでしょうか？

  なぜインスタンスに直接ログを保存するのが避けられるのか

 1. アクセス制御や閲覧権限の管理が複雑になる
 • ローカルファイルとしてログを保持している場合、オペレーティングシステムレベルのアクセス権限設定や、ログインできるユーザー（またはアプリケーション実行ユーザー）に依存してしまいます。
 • 例えば「マネージャー以上の権限を持つ人しかユーザー情報のログを閲覧できない」などの要件がある場合、OS上のユーザーやグループを細かく管理する必要があります。昇格・降格などの人事があるたびにサーバー管理者が手動で調整するのは運用負荷が大きく、誤操作も生じやすいです。
 • 一方で、集中管理されたログ管理サービス（例: ELK Stack, Splunk, SaaS系のログ管理ソリューションなど）を利用すると、アプリケーションの役職/ロールに紐付いたロールベースアクセス制御(RBAC)で権限管理を行いやすくなります。
 2. 誰がいつどのログを閲覧/編集したかの監査が難しい
 • ローカルファイルに対して「閲覧履歴」や「編集履歴」を実装するのは、OSが提供する監査ログ機能などを活用しても手間がかかり、かつログの検索・分析がしづらいです。
 • 中央集約型のログ管理サービスを使えば、ログの閲覧・検索の操作自体もサービス側で監査ログに残せるようになっていることが多く、誰がいつ何のログを参照したのかを管理者が容易に追跡できます。
 3. インスタンス数が増えるとログが分散してしまい、集約が困難
 • マイクロサービスやオートスケーリング環境などでは、同種のサービスを多数のインスタンスで並行稼働させることが一般的です。それぞれのインスタンスが独自にログをローカルに保存していた場合、エラー調査や障害時の原因追跡で必要になる「全インスタンス分のログを横断的に検索・参照する」ことが大変になり、SCPやrsync、SSHログインなどを駆使して手動で集めることになりがちです。
 • これを避けるためにも、各インスタンスで発生したログはすぐに外部のログ集約サーバーやクラウドのログサービス(例: Cloud Logging, Elasticsearch, Datadogなど)に送ってしまい、リアルタイムで一元管理するのが主流です。
 4. インスタンスのストレージをログが圧迫するリスク
 • 大規模システムや高トラフィックサービスでは、インスタンス上に出力されるログが非常に大容量になることがあります。
 • ローカルディスクの容量を優先的にアプリやデータベース用に割り当てたい場合、ログが肥大化してディスクを圧迫するのは好ましくありません。
 • また、ディスクが一杯になるとサービスダウンの原因にもなるため、ログを外部ストレージに送って保持するか、もしくはログのローテーションを厳密に制御して一定期間経過したログはアーカイブへ移すなどの運用が必要です。しかしこれらも外部のログ管理基盤を用いた方が安全かつ効率的です。

「food for thought」に対する考え方

 1. 権限管理をどのように行うか
 • ログ管理ツールやサービスで RBAC (Role-Based Access Control) を利用する。
 • 例えば「Userに関するログはManagerロール以上しか見られない」という設定をツール側のUIやコンフィグで行う。
 • マネージャーの降格時など、役職変更があればツール上のロール設定を変更するだけで運用が完結し、ログ管理サーバー上の閲覧権限も自動的に更新される。
 2. 特定のログへのアクセス履歴・編集履歴の追跡
 • 監査ログ(Audit log)機能を提供するログ管理サービスを利用する。
 • いつ・誰が・どのログを検索した/閲覧した/エクスポートしたのか、といった操作履歴が自動で記録される。
 • もし編集（マスキングや削除など）が必要な場合は、編集操作も監査ログに残るようにするか、あるいは改ざん困難なストレージ(イミュータブルストレージ等)を併用して「編集はできない」運用にすることもある。
 3. 複数インスタンスに分散されたログの集約
 • 各インスタンスから標準出力（stdout, stderr）やログファイルを fluentd, Logstash, Vector, Filebeat, Cloud Logging Agent 等を用いて外部に集約する。
 • 集約先であるElasticsearchやS3、クラウドのログストレージ等に一元的に保管し、KibanaやGrafanaなどを使って横断検索・可視化する。
 • サービス規模が大きいほど、ローカルファイルを手動で集める方法は非現実的になるため必須の仕組みといえる。
 4. ログファイルによるストレージ逼迫のリスク
 • ローカルディスクが埋まる前にローテーションさせ、外部ストレージやアーカイブに移す仕組みを導入する。
 • あるいはそもそも短期間のみローカルに保持し、即座に外部ログ管理サーバーに送信してローカルには保持しない運用にする。
 • クラウドサービス上のマネージドログストレージではスケールが担保されやすく、期限・容量に応じた自動アーカイブや削除も設定できる。
